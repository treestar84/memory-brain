## 왜 `e9559ca`가 나왔는가 — 실효성 검증 1라운드 사고 경위

"memory-brain이 실제 효능이 있는지 제3자 관점에서 검증해야 한다"는 문제의식으로 클린 서브에이전트 2개(A=1일차 vibe coding 작업, B=블라인드 인수인계)를 순차 소환했다.

- **A**: 실제 프로젝트(`splitpot`, 비용정산 CLI) 만들고, 실제 버그(1센트 증발) 겪고, 실제 `cfgm capture → accept → rebuild-index` 파이프라인을 손으로 밟음. 그런데 `CFGM_PROJECT_ROOT`를 안 정해서 cwd가 memory-brain 툴 저장소 자체(`/Users/treestar/dev/memory-brain`)로 잡혔고, A의 하루치 기억이 **자기 프로젝트가 아니라 툴 저장소 자체의 `memory/`**에 기록됐다.
- **A 본인은 이 오류를 못 잡았다** — 자기가 쓴 바로 그 (잘못된) 위치에서 다시 읽으니 "retrieval이 잘 된다"고 확증편향에 빠져 보고함. **같은 프로세스/같은 습관이 쓰기와 읽기를 모두 수행하면, cwd 오류 같은 클래스의 버그는 자기검증으로 절대 못 잡는다** — 이게 이번 라운드의 핵심 방법론적 교훈.
- **오케스트레이터(나)**: A 완료 후 저장소 오염을 발견하고 **삭제로 정리**했는데, 이게 A의 유일한 기억 사본이었다. 검증 없이 삭제한 것 자체가 실험을 파괴하는 개입이었다.
- **B**: 블라인드로 인수인계 받았을 때 memory-brain엔 아무것도 없었다("검색 인덱스가 없습니다"). 결국 평범한 markdown 세션 노트 파일을 직접 읽어서 인수인계를 완수함 — **도구가 실패한 게 아니라 애초에 데이터가 없었다**는 걸 B가 스스로 정확히 짚어냄.

이 연쇄 자체가 실사용에서 벌어질 수 있는 진짜 데이터 유실 시나리오(bun link PATH 문제로 절대경로 우회 → CFGM_PROJECT_ROOT 깜빡함 → 나중에 툴 저장소 정리/재설치 → 조용히 기억 소실)임을 확인했고, `e9559ca`로 근본 수정했다.

## 다음 세션에서 할 일 — 개선된 검증 프로토콜 (아직 실행 안 함)

`resolveRepoRoot()` 경고가 이제 존재하므로 같은 사고가 재발할 확률은 낮아졌지만, **1라운드는 진짜 검증 목표(검색 복원 정확도)를 한 번도 제대로 못 쟀다** — 재실행이 필요하다. 사용자와 합의된 개선점:

### 구조: A → C(체크포인트) → B, 3단계로 확장

```
A (1일차 작업 — 이전과 동일한 역할)
  ↓
C (독립 체크포인트 에이전트 — 신규)
  ↓ (C가 통과시켰을 때만 B 진행)
B (블라인드 인수인계 — 이전과 동일한 역할)
```

**핵심 원칙 — 반드시 지킬 것:**

1. **C는 A/B 둘 다와 완전히 독립된 제3의 클린 에이전트**여야 한다. A 자신에게 "다시 검증해봐"를 시키면 안 됨(자기가 쓴 곳에서 자기가 읽으면 cwd 버그 같은 클래스는 절대 못 잡는다는 게 1라운드의 교훈).
2. **C의 임무는 딱 하나**: `<A의 프로젝트 경로>`에 memory-brain이 실제로, 올바른 위치에 셋업됐는지 기계적으로 확인만 한다. A의 "성공했다"는 자기 보고를 신뢰하지 않고 독립적으로 재확인.
   - `<프로젝트 경로>/memory/` 에 실제 wiki 페이지(`decisions/`, `concepts/`, `projects/`)가 있는가
   - `<프로젝트 경로>/.memory-brain/indexes/search.sqlite` (또는 `CFGM_PROJECT_ROOT` 기준 storage root)가 존재하고 비어있지 않은가
   - A가 언급 안 한, C 스스로 만든 임의 키워드로 `cfgm search`를 던져서 실제 hit이 나오는가
   - **memory-brain 툴 저장소 자체(`/Users/treestar/dev/memory-brain/memory/`)에 A의 흔적이 새어 들어갔는지도 확인** — `e9559ca` 경고가 실제로 떴는지/안 떴는지까지 보고에 포함
3. **C가 실패 판정하면 그 자리에서 멈추고 보고 — B를 진행하지 않는다.** 밑 빠진 독에 B의 시간을 낭비하지 않기 위함.
4. **C가 통과시키면 "확인됨" 신호만 B에게 전달** — 기술적 내용(A가 뭘 만들었는지)은 여전히 B에게 안 알려줌, 블라인드 유지.
5. **오케스트레이터(다음 세션 담당자)는 실험 중 삭제 금지.** 오염 발견 시 지우지 말고 옮기거나 백업부터 — 삭제가 곧 실험 파괴였던 1라운드 실수를 반복하지 말 것.
6. **A에게 "성공했다" 서술 대신 진단 경로를 raw로 출력하게 강제**한다 — `resolveStorageRoot()`/`resolveRepoRoot()`가 실제로 어떤 값을 반환했는지 그대로 보고에 포함시키도록 프롬프트에 명시. 사람이 읽고 이상한 경로면 즉시 알아챌 수 있게.

### 아직 결정 안 된 것 — 사용자에게 확인 필요

**세트 수**: 1세트(A→C→B)만 다시 돌릴지, 아니면 재현성 확인을 위해 2~3세트를 병렬로 돌릴지. 이전 세션에서 이 질문을 사용자에게 던졌으나 세션이 종료되어 답을 못 받음. 다음 세션 시작 시 다시 물어볼 것.
